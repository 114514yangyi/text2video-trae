## 0. 一句话结论

导师说得对：旧数字（22–26）**不是 FVD**。旧实现用 torchvision R(2+1)D-18 的 512 维
average-pool 特征，而官方 FVD 用的是 **Kinetics-400 预训练 I3D（Inception-v1）的 400 维
logits**。换骨干 = 换特征空间，Fréchet 距离没有物理单位，两者之间不存在换算关系；旧数字
整体作废，不得再与任何文献或新数字并列。

修复后（2026-10-21）实测：自检 **133.91**（官方 0-vs-255 参考 ~131）；四条基线重算
**132.30–184.67**（真值半分本底 74.17）。这个量级与文献手语域 FVD（几百到 ~1700）一致，
而旧口径的 22–26 只是"R(2+1)D 池化特征空间里的一个数"，与 FVD 无关。

## 1. 官方 FVD 是什么（论文 + 参考代码）

来源：Unterthiner et al., *Towards Accurate Generative Models of Video: A New Metric &
Challenges*, arXiv:1812.01717；官方代码
`google-research/frechet_video_distance/frechet_video_distance.py`；
TF-Hub `deepmind/i3d-kinetics-400/1`。

| 项目 | 官方取值 | 说明 |
|------|----------|------|
| 骨干 | I3D（Inception-v1，膨胀 3D 卷积），Kinetics-400 RGB | 不是 R(2+1)D，也不是 Inception-v3 |
| 特征层 | **Kinetics-400 logits（400 维，softmax 前）** | 论文原文 "evaluate the logits in the final layer, as well as the output of the last pooling layer"，噪声实验后选定 logits；官方代码注释 `# gets the kinetics-i3d-400-logits layer` |
| 帧数 | 时间维全卷积，不强制 64；论文评测用 16 帧（BAIR）或 20 帧（KTH） | 参考实现允许短片段；本项目固定 16 帧 |
| 预处理 | 双线性 resize 到 224×224，像素 0–255 → **[-1, 1]** | 官方 `resize_bilinear` 直接到 224 |
| 距离 | `‖μ_r−μ_g‖² + Tr(Σ_r+Σ_g−2(Σ_rΣ_g)^{1/2})`，float64 | 400 维高斯假设 |
| 单位/量级 | 特征空间平方距离，无物理单位；同数据集同协议内才可比 | 论文 §4.3.1：FVD 差 < 50 人类几乎分不出，≥ 50 才算可感知 |
| 有限样本 | 同分布时 FVD 也 > 0（§4.2） | 因此必须报告 N 与 real-vs-real 本底 |

**关键澄清**：官方 `Mean:0` 这个 tensor 名字容易被误读成 1024/2048 维 average-pool。但
universome/fvd-comparison 证明 PyTorch torchscript 移植（固定输出 400 维）与 TF-Hub 图
逐元素 L2 = 2.6e-4、FVD 差 1e-6；`common_metrics_on_video_quality` 也明确写
"size of the last dimension is 400, not 1024"。所以**官方特征就是 400 维 logits**。

**文献量级（供 sanity check，不是标尺）**：

- 原论文：BAIR 116.4–315.5；KTH 78.0–208.4；SCV-MUtB 276.7–710.5；Brawl 714.5–1295.4；RTwM 698.6–2031.4。
- StyleGAN-V：FaceForensics-256² FVD16 47.41；SkyTimelapse 79.52；UCF-101 1431.0（MoCoGAN 2886.9）。
- 手语/PHOENIX14T：已发表工作中 RWTH-2014T（= PHOENIX14T，test 642）报 **FVD 1025.45**
  （同领域其它工作 1431.38、1715.32 量级）；FlashSign 453–597；How2Sign 2207.67。
  → 256² 手语视频的官方 I3D-FVD 合理区间是**几百**（约 400–1700）。22–26 明显异常。

## 2. 旧实现错在哪（逐项对照）

旧 `tools/eval_fvd.py`（2026-10-18 至 2026-10-21）：

| 项目 | 旧实现 | 官方 | 后果 |
|------|--------|------|------|
| 骨干 | torchvision R(2+1)D-18（Kinetics-400） | I3D Inception-v1（Kinetics-400） | 特征空间完全不同 |
| 特征层 | `fc = Identity` 后的 512 维 pooled 特征 | 400 维 logits | 全局池化抹平方差/协方差；logits 保留类级尖峰 |
| 特征尺度 | ReLU 后 O(1) | 无界类别分数 O(10) | Fréchet 是平方距离，尺度差 s 倍 → FVD 差 s² 倍 |
| 预处理 | 先 Resize(256)+CenterCrop(256)，再套 ImageNet 权重自带的 Resize(128)+Crop(112) | resize 224 + center crop 224 + [-1,1] | 有效分辨率只有 112²，且归一化是 ImageNet 均值/方差 |
| 帧数 | 16（同） | 16–20（同量级） | 不是主因 |
| 数值 | 22–26（N=642） | 手语域应几百 | 差 1–2 个数量级 |

结论：**数值异常的主因是骨干+特征层（512-d avgpool vs 400-d logits）与预处理口径**，
不是 Fréchet 公式本身。公式（sqrtm + trace）与真/生成同规则采样这两点旧实现是对的，保留。

## 3. 本仓库 FVD 协议 v1（唯一口径）

实现：`tools/eval_fvd.py`（自检 `--self-check`）。

| 项目 | 本项目取值 |
|------|-----------|
| 指标全称 | **FVD (I3D-K400 logits, 16 frames, 224²)** |
| 骨干/权重 | I3D Inception-v1 Kinetics-400，torchscript 权重 `models/i3d/i3d_torchscript.pt`，sha256 `bec6519f66ea534e953026b4ae2c65553c17bf105611c746d904657e5860a5e2` |
| 特征 | 400 维 logits（`return_features=True`，不过 softmax） |
| 帧采样 | 每条视频**均匀取 16 帧**（`np.linspace` 覆盖全序列）；生成帧取 `latents.pt` 第 1..T 帧，真值帧同步跳过第 0 帧（第 0 帧是条件参考帧，不参与生成） |
| 预处理 | 短边 bilinear（antialias）缩到 224 → center crop 224 → `(x−0.5)×2` → [-1,1] |
| 距离 | float64，`scipy.linalg.sqrtm`，`‖Δμ‖² + Tr(Σr+Σg−2(ΣrΣg)^½)` |
| 样本 | test 642 单侧（`RULES.md` 评测规范第 6 条）；同一对比内 N、seed、采样器/NFE/CFG/长度口径必须一致 |
| 缓存 | 真值特征 `reports/eval/fvd_ref/<split>_<sha1(ids)[:12]>_f16_i3d400.npz`；缓存校验 ids/frame 数/backbone，三者任一不符即重算 |
| 报告字段 | `fvd`、`num_videos`、`real_split_half_fvd`（真值前后半本底）、`mean_feature_l2`、`video_ids`、`protocol{backbone,feature_layer,feature_dim,num_frames,frame_sampling,preprocess,distance,weights_sha256}` |
| 权重获取 | `python tools/fetch_i3d_weights.py`（HF 镜像 `hf-mirror.com`，校验 sha256） |
| 帧重建 | `python tools/redecode_fvd_frames.py --run <run_dir> --num-frames 16 --workers 6`（从 `latents.pt` 只解码 16 个等距 latent 行，输出 `<run>/fvd_frames16/<split>/<video_id>/images*.png`） |

**为什么真值跳过第 0 帧**：本项目的生成条件是 frame 0（`conditioning.reference`），
`latents.pt` 的第 t 行对应视频第 t+1 帧。FVD 对比的是"生成帧 vs 同序号真值帧"，
因此真值侧同样取 `[1..T]`，两侧在相同相对时间位置均匀取 16 帧。

**自检（每次改 FVD 代码后必须跑）**：

```bash
python tools/eval_fvd.py --self-check --out reports/eval/fvd_selfcheck.json
```

官方 `example.py` 的口径：16 条 15 帧 64×64 全 0 vs 全 255 → FVD ≈ 131。
本实现 2026-10-21 实测 **133.91**（差异来自 resize 插值实现），判据 `100 < FVD < 180`。
正常运行的报告还会写 `real_split_half_fvd`：把 642 条真值分两半互相算 FVD，
它是"有限样本本底"；模型 FVD 若低于这个本底，先怀疑管线而不是庆祝。
2026-10-21 实测（N=642，16 帧，400-d logits）：**前半 vs 后半 = 74.17**，
**奇偶交错半分 = 59.18**；即同一批真值的有限样本本底约 **60–75**，不是 0。

## 3.2 样本量偏差：FVD 不能跨 N 比较（2026-10-22 实测）

起因：用外部已发布方法的官方权重复现 642 条 test 生成视频，用其官方口径（32 帧连续、272×224、
I3D 400-d logits、`only_final=True`）算得 **259.00**，而论文 RWTH-2014T 表为 **1025.45**。
为定位差异，固定同一批生成帧与同一份真值特征，**只改变抽取的视频子集大小**重算：

| N | 生成 vs 真值 FVD | 真值 split-half 本底 | 同口径 prefix60k |
|---|------------------|----------------------|------------------|
| 20 | **907.1** | 1488.1 | 727.1 |
| 40 | 660.8 | 823.7 | 555.4 |
| 60 | 514.0 | 545.0 | — |
| 80 | 457.0 | 469.1 | 431.5 |
| 160 | 344.6 | 332.8 | — |
| 320 | 284.6 | 163.9 | — |
| 634 | **259.0** | 86.3 | 239.9 |

- 同一模型、同一批输出，仅 N 从 634 降到 20，数值就从 259 → 907，本底从 86 → 1488。
- 更旧的 `prefix60k` 完全服从同一曲线（N=20 时 727），说明膨胀来自**估计量本身**，不是模型变差。
- 一阶偏差模型拟合（N=320/634 两点）：`F(N) ≈ 233 + 1.65×10⁴ / N`；外推 N=20 时 ≈1057。
  即 N 越小，有限样本噪声（协方差估计误差）越大，FVD 被系统性地抬高。
- **规则**：跨 N 不可比。N<80 时本底 >400，只能用于冒烟/看趋势；正式比较必须 N≥300，
  本仓库默认用 test 全量 634–642。报数必须带 N 与本底。

再把 N 扫到 10（另一个 60 条特征池，逐点取前缀）：

| N | 10 | 15 | 20 | 25 | 30 | 40 | 60 |
|---|----|----|----|----|----|----|----|
| FVD | **1005.16** | 1005.00 | 969.00 | 867.22 | 790.15 | 656.46 | 531.32 |

- N=10 的 1005.16 与论文 1025.45 **量级相容**（差约 2%），但这是"相容"而不是"证明"：
  论文正文未公开 FVD 的 N/帧数/分辨率，仓库唯一的 FVD 调用（`log_valid`）只证明**训练期验证
  至多 10 条**，不等于论文表格协议。因此只能说 1025.45 与小样本口径相容，**不能断言论文 N=10**。
- 不同子集池之间有 ±10% 抖动（N=20 在 150 池上 907、在 60 池上 969）——这就是小 N 噪声本身。
- 正确结论：**259.00（N=634）与 1025.45 口径不同，不可直接相减**；同模型不同 N 的数值不能
  当成"差 4 倍"来读。

退化基线（N=150，同一真值集），用于标定"1025 有多差"：

| 输入 | FVD |
|------|-----|
| 生成（本机复现） | 343.0 |
| 时间乱序（外观保留、运动破坏） | 901.1 |
| 冻结首帧重复（无运动） | 1156.4 |
| 真值 test vs 真值 train（不同说话人） | 229.0 |

在 N≈150 口径下，1025 介于"时间乱序"与"冻结帧"之间。若论文在同一 N 口径下评测，这个量级
与其模型能力不相称，因此**更可能**是论文采用了更小的样本量或另一套未公开协议（这是推断，
不是已证明的事实；需要用作者脚本/日志确认）。

### 外部工作的官方验证代码实际是 10 条

所引外部方法的仓库训练脚本在验证循环里 `batch_size=1`、`max_eval_batches` 默认 **10**；条件用
**GT pose**、参考帧从同视频随机取、`video_length=32`；FVD 在该循环里对 ≤10 条样本算一次。
该仓库内**没有**面向论文表格的独立 test 评测脚本，论文正文也未写 FVD 的 N/帧数/分辨率。
因此"1025.45"与"642 条 test 的 259.00"**不是同一口径**，直接相减没有意义。

## 5. 报告与引用规则（强制）

1. **写全称**：`FVD (I3D-K400 logits, 16 frames, 224², N=642)`。只写 "FVD" 时必须能从同段
   文字或 `fvd.json` 的 `protocol` 块读到这四项。
2. **禁止混表**：旧 `FVD (R(2+1)D-18 avgpool, 512-d)` 数字（22.437 / 25.998 / 25.667 /
   23.584，以及所有 N=32 的 51.6–58.4）**作废**，只保留在历史日志里作追溯；不得与官方
   I3D-FVD 出现在同一张对比表。
3. **禁止跨数据集/跨帧数比较**：文献数字只有在数据集、帧数、分辨率、N 都对齐时才可并列；
   手语域合理区间几百，22–26 不可能是同一口径。
4. **FVD 差值解读**：同协议内差值 < 50 视为不可感知（论文 §4.3.1），不要拿 1–5 的
   FVD 波动去宣称方法有效；要同时看 `real_split_half_fvd` 本底与配对显著性。
5. **旧 doc 的处理**：`EXPERIMENT.md` 第 5 节历史 FD 列保留原文（自动生成区），但表头与
   备注必须标注"旧 R(2+1)D 口径，已作废"；新表的 FD 列必须来自新协议。
6. **回译指标**：自 2026-10-21 起**不再要求、不再作为对比/晋级指标**（用户指令）。
   如个别分析仍要看回译，只作可选诊断，仍走 SignMbart 口径，且不得与 FVD 主表混排。
7. **N 与本底必须同时报告**（2026-10-22 增补，见 §3.2）：任何 FVD 数字必须带
   `N` 与 `real_split_half_fvd` 本底。跨 N 的 FVD **禁止比较**（本机实测同一批输出
   N=20→907、N=634→259）；与论文/他文数字比较前必须先确认其 N、帧数、分辨率、
   条件与样本来源，无法确认时只能写"口径不可比"。

## 6. 复现命令

```bash
# 0) 权重（一次性）
python tools/fetch_i3d_weights.py

# 1) 自检（必须 ~131）
python tools/eval_fvd.py --self-check

# 2) 真值特征缓存（一次性，642 test）
python tools/eval_fvd.py --fill-ref-cache --split test

# 3) 从 latents 重建 FVD 所需的 16 帧
python tools/redecode_fvd_frames.py \
  --run reports/eval/matrix/route_t_align_20k/test_n642 --num-frames 16 --workers 6

# 4) 算 FVD
python tools/eval_fvd.py \
  --generated reports/eval/matrix/route_t_align_20k/test_n642/fvd_frames16 \
  --split test --num-frames 16 --out reports/eval/matrix/route_t_align_20k/test_n642/fvd_i3d400.json
```

## 7. 已知限制与后续

- 当前 shell 无 `/dev/nvidia*`（GPU 设备节点缺失），VAE 解码与 I3D 特征都在 CPU 上跑：
  解码 16 帧约 10–20 min/臂，特征提取约 10–15 min/臂（642 条）。2026-10-21 已按此完成
  四条基线重算；GPU 恢复后建议抽一条臂复跑，确认 CPU 与 CUDA 的数值一致（同一权重、同一
  预处理，理论上只差浮点舍入，但仍应实测）。
- `real_split_half_fvd` 随 N 增大而下降，N=642 时才是稳定本底；小样本诊断请注明 N。
- 旧 `reports/eval/matrix/*/fvd.json` 与新 `fvd_i3d400.json` 并存，前者**不得**再被
  `collect_experiment_table.py` 当作 FD 列来源（已在该脚本里改表头/来源）。
- 文献数字的帧数/分辨率/N 常不写全；跨论文比较前先确认对方协议，禁止把本表 132–185
  直接与协议未写全的外部数字相减（见 §5 第 3 条）。
